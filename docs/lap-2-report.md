## この文書での言葉

- **作成担当**: 工場を直し、この報告を書いたエージェント（claude-org のワーカーとして動いた Claude Code）。
- **実行担当**: モデルの API に出られる端末で工場のコマンドを叩いた担当（claude-org の窓口役）。オーナーとの連絡も受け持った。
- **前提 1〜3**: 設計書の末尾「試作で最初に確かめる、一番危うい前提」の番号。
  - 1: 作る役にシナリオを見せなければ、合わせ込みは防げる。
  - 2: 人に戻らなくても、やり直しで収束する。
  - 3: 費用を全量計上できる。
- **仕様の下書き役 / シナリオの下書き役**: この周で下書き役を 2 つの別セッションに分けた。
  - 仕様の下書き役は、仕様・仮定・インタフェースを書く。
  - シナリオの下書き役は、仕様を見ずに隠しシナリオを書く。
- **インタフェース**: 仕様の下書き役が出す「名前と形」だけのブロック。中身は、エンドポイント、クエリ名、フィールド名、一覧の形、競合を見分ける値の置き場所。状態コードや振る舞いの規則は入れない。
- **独立した分類**: シナリオごとに付ける「仕様から読み取れるか」の印。下書き役の自己申告ではなく、工場の手続きで付ける。
  - 手続き: 仕様と既存コードだけを見た別セッションに、各要求への応答を予測させる。予測を、シナリオの期待値と機械的に照合する。
  - 印は 4 つある。`readable`（読み取れる）、`contradicts`（仕様と食い違う）、`unstated`（仕様が決めていない）、`unknown`（分類できなかった）。
  - 読み取れる場合は、根拠を次の 3 つから記録する。
    - 仕様（spec）
    - 既存コード（code）
    - HTTP の一般的な慣習（convention）
- **自己申告（inSpec）**: シナリオの下書き役が、シナリオごとに付けた自分の申告。この周では「依頼文にこの振る舞いが書いてある」の意味。1 周目は「仕様に書いてある」の意味だったので、両周の自己申告の数字はそのまま比べられない。
- **食い違い一覧**: 入口の要約に載せる 2 部の一覧。
  - (a) 仕様と食い違うシナリオ（`contradicts`）
  - (b) 仕様が決めていないことを求めるシナリオ（`unstated`）

  工場は直さず、オーナーが承認するか出し直すかを決める。
- **変更 id**: この周には 2 つあった。`memo-tags-1` は最初の下書きで、承認していない。`memo-tags-2` は出し直した下書きで、承認して出荷した。

## 工場に入れた変更

1. **下書きを 2 つのセッションに分けた。**
   - 仕様の下書き役は、仕様・仮定・インタフェースを返す。インタフェースは、仕様の末尾にもそのまま付ける。作る役が、シナリオと同じ名前を使えるようにするためである。
   - シナリオの下書き役が受け取るのは、依頼文・拡張元のアプリの現コード・インタフェースだけ。仕様も、仕様の下書き役の仮定も受け取らない。
   - どちらのセッションも道具を持たず（ツールなし）、保管庫の見えない sandbox で動く。
2. **「仕様から読み取れるか」を独立した手続きで決める。**
   - シナリオごとに別セッションを 1 回呼ぶ。このセッションに見せるのは、仕様・既存コード・要求の並びだけである。期待値・id・題名・要約・種類は見せない。
   - 予測の決まらない部分は、「?」か「省略」として扱わせる。予測と期待値を、照合 1 件ずつ「一致 / 食い違い / 決まらない」の 3 値で比べる。
   - 仕様やコードを根拠と称しても、その引用が本文に実在しなければ、根拠を「慣習」に格下げする。
   - 分類の結果（`classification.json`）は、承認する組に含める。通過率は、自己申告と独立した分類の両方で分けて記録する。
3. **入口の要約に、分類の表と食い違い一覧 (a)(b) を載せる。** 工場は食い違いを直さない。
4. **拡張元の版を固定する。** `draft --base <出荷先>` で読んだ commit を、承認の版に含める（`base.json`）。run の時点で出荷先の HEAD が違えば、作る前に失敗で終える。
5. **シナリオの書式を足した。** 依頼に一覧のページ分けと同時更新が入るため、次の 3 つを足した。
   - 本文の中の配列の件数の照合（`length: {"items": 2}`）
   - レスポンスヘッダからの値の取り出し（`capture: {"v": "header:etag"}`）
   - リクエストヘッダへの値の埋め込み（これまで `{{name}}` がヘッダでは置き換わらなかった不具合の修正）
6. **費用の計上を細かくした。**
   - 分類の呼び出しは、1 回 $0.50 までにした。
   - 費用を報告しない呼び出しは、上限の残り全額ではなく、その呼び出しに許した額で計上する。
   - 下書き役の各呼び出しは $1 まで。下書き全体の上限 $10 の中に、分類の分が収まるようにした。
7. **下書きの返答が検査に落ちたら、1 回だけ書き直させる。** 新しいセッションに、同じ入力・前の返答・落ちた理由を渡す。検査は緩めない。

### 読み取れること

- **memo-tags-1: 仮定の文が仕様の規則を運んだ。**
  - インタフェースのブロックは、約束どおり名前と形だけだった。しかし、仕様の下書き役は、インタフェースとは別の自由文の仮定 17 件に、規則をほぼすべて書いていた。例: AND で絞り込む、大文字と小文字を区別しない部分一致、既定 20 件・最大 100 件、古い版番号には 409。
  - これがシナリオの下書き役へ渡った。設計で「振る舞いの規則は渡さない」と決めた線が、仮定の欄から崩れた。
- **memo-tags-2: 通り道を塞いでも、全数が読み取れた。**
  - シナリオの下書き役は、依頼文から決まらないことを避けて書いた。
    - 状態コードは「409 か 412」の幅で書いた（工場がそう指示している）。
    - 大文字と小文字の扱い、既定のページ件数、版番号の初期値は確かめなかった。書き手の仮定に、その旨が残っている。例: 「語の検索は保存した文字と同じ大小で試す」「件数を指定しないときは、少なくとも 3 件が 1 ページに来る」「版番号の型は仮定しない」。
  - 仕様は細かく、残った範囲をすべて決めていた。
  - 1 か所だけ、書き手の仮定が仕様と食い違った。仮定は「タグは大文字と小文字を区別する」、仕様は「小文字にそろえる」。ただ、シナリオがそこを確かめていないので、一覧には出ない。
- **前提 1 の懸念は、書き手を分けても消えなかった。**
  - 懸念とは、判定が作る役の思い込みと同じものを測るだけになる、というもの。
  - 隠しシナリオが確かめていることは、詳しい仕様の内側にすべて入っていた。作る役は仕様に沿うだけで通る。
- **ただし、1 周目より言えることは強くなった。**
  - 今回のシナリオは、仕様を見ていない書き手が依頼文から独立に書いたものである。合格は「仕様の言い回しに合わせた」のではなく、「依頼文の独立した読み方の範囲で、作ったものが正しく動いた」ことを示す。
  - また、1 周目では作成担当が手で付け直していた分類を、工場の手続きで付けられるようになった。

## 既知の限界

- **分類は 1 回だけの標本。**
  - シナリオごとに予測を 1 回しか取っていない（費用を優先したオーナー判断）。予測が「?」か具体値かは、呼ぶたびに揺れうる。
  - この周は全数が一致したので、境界での揺れは観測されていない。
- **「読み取れる」の意味。**
  - 分類が示すのは、「シナリオが確かめていることを、仕様が決めているか」である。シナリオの書き手が依頼文だけから慎重に書くと、確かめる中身は、詳しい仕様ならどれでも決めている範囲に寄る。
  - そのため、全数「読み取れる」は、「隠しシナリオが仕様の外を確かめていない」ことを示すにとどまる。合わせ込みが起きたことの証拠ではない。
- **慣習の扱い。**
  - 根拠が「慣習」だけの一致も、「読み取れる」に数える。そのうえで内訳を出す。この周では、慣習だけの一致は 0 件だった。
  - 引用が仕様に実在するかは、空白をそろえた部分一致で確かめている。言い換えた引用は、慣習に格下げされる。
- **memo-tags-1 の 1 回目の失敗について。**
  - 失敗した下書きの返答は、記録に残していない（費用だけが残る）。どの値が要約に入っていたかは、後から確かめられない。
  - 失敗の文面に漏れた値を出すようにしたのは、この失敗の後である。
- **Codex のレビューの範囲。**
  - 上限 3 ラウンドの後に入れた変更は、オーナーが承認した追加 1 ラウンドで見た。対象は、1 回だけ書き直させる仕組み（下書きの返答が検査に落ちたとき）と、シナリオの下書き役に仮定を渡さない変更。
- **sandbox の中の `~/.claude.json`。**
  - 隔離の確認で、sandbox の中の `~/.claude.json` は約 58KB あった。工場が渡すのは、許可したキーだけの写し（呼び出しごとの使い捨てで、ホストへは書き戻らない）である。
  - CLI が起動中に、自分で書き足したものと見ている。中身は確かめていない。
- **1 周目から引き継いでいる限界。**
  - lap 台帳には、ロックが無い。
  - 合成トラフィックは、メモ API の形に固定している。
  - アプリが 127.0.0.1 以外で待ち受けていないかは、起動時にだけ確かめる。
  - 作る役は認証トークンを読める。

## 次の周への提案（判断はオーナー）

1. **前提 1 は、シナリオの書き手を分けるだけでは足りないと分かった。** 次は、書き手が依頼文から決まらない所を避けないようにする。
   - 案 A: 「依頼文から決まらない所こそ、自分の判断で値を決めて確かめよ」と指示する。そのうえで、仕様と食い違ったものを (a) に出させる。
   - 案 B: 仕様の下書き役には、振る舞いの要点だけを書かせる。細部は、シナリオ側だけに置く。
   - どちらも、食い違いが増えれば、入口でオーナーが読む量が増える。
2. **前提 2 を試すには、仕様と食い違うシナリオを含む組を、あえて承認して走らせる必要がある。**
   - 上の案 A で (a) が出たときに、オーナーがそのまま承認すれば試せる。
   - 作る役は仕様に従うので、食い違ったシナリオは落ち続け、上限で失敗に終わるはずである。それを確かめるのが前提 2 の厳しい側の試験になる。
3. **分類の費用は、出荷した変更の半分を占めた。** 安くするなら、次の 2 案がある。
   - シナリオ数本をまとめて 1 セッションで予測させる。シナリオの間で手掛かりが漏れるので、測り方が少し甘くなる。
   - 分類役だけ、小さいモデルにする。
4. 設計書 2 章の線（下書き役に見せるもの・渡すもの）を、この周の結果に合わせて書き足す。変更案は窓口に渡した。

## 設計書 2 章の変更案（窓口が factory-notes に反映する）

- 下書き役の行を、2 行に分ける。
  - 仕様の下書き役に見えるもの: 入口の依頼、本番シグナル、拡張する既存アプリの現コード（読むだけ）。
  - シナリオの下書き役に見えるもの: 入口の依頼、本番シグナル、拡張する既存アプリの現コード（読むだけ）、インタフェース（名前と形だけ）。仕様と、仕様の下書き役の仮定は見えない。
- 仕様の下書き役からシナリオの下書き役へ渡すのは、インタフェースだけにする。振る舞いの規則も仮定の文も渡さない。
  - 当初の指示は「依頼文と仮定を渡す」だった。2026-10-17 のオーナー判断で、仮定の文を外した。理由は、memo-tags-1 で仮定が規則の通り道になったため。
- 「仕様から読み取れるか」は、別の手続きで判定する。仕様と既存コードだけを見た別セッションに応答を予測させ、機械的に照合する。
- 食い違いは、入口の要約に 2 部の一覧として載せる。工場は自動で直さない。
