### なぜ一度で全部を当てたか

仕様が決めていない 95 件の照合（U）それぞれについて、作る役の答えが通った理由を記録から分析した。

- 材料: 保管庫の仕様・シナリオ・分類、拡張元 `b36ad38` と出荷物 `d9320cb` のコード、シナリオの下書き役の仮定。
- 方法: Claude Code の多エージェント実行（ultracode）で、4 つの分析エージェントがシナリオを分担して付け、別の 1 エージェントが、影響の大きい 10 件の付け方を検証して直した。

| 決め手 | 照合の数 | 例 |
|---|---|---|
| A 既存アプリの規則 | 50 | 戻しでも version を +1 する（既存の更新と同じ）。履歴の limit は 1〜100・既定 20・不正なら 400（既存の `GET /memos` の解析をそのまま切り出した）。存在しないメモは 404。古い version は 409 `{error, current}` |
| B 一般的な慣習 | 3 | 履歴の取得が 200 |
| C シナリオの許容 | 20 | 戻しの成功は 200 か 201 のどちらでも通る。不正な入力は 400 か 422。フィールドがあるかだけを見る照合 |
| D 仕様の本文・インタフェース・依頼文 | 22 | インタフェースの `action` の値に `"create"` があり、作成も履歴に入ると読める。履歴の項目は「その版の内容」とある |
| E たまたまの一致 | 0 | — |

特に効いたのは次の 3 点。

1. **シナリオの下書き役も、同じ既存コードを読んで書いていた。**
   - 仮定に「履歴のページ分けは GET /memos と同じ規則（limit 1〜100、既定 20、不正は 400）」「並び順は GET /memos と同じく古い順」「戻しも PATCH・PUT と同じく version が要る」とある。
   - 作る役も、同じ規則をそのまま使った。両者が同じ源を見ていたので、仕様を未定にしても答えはそろう。
2. **インタフェースが、未定の 1 項目を事実上決めていた。**
   - 未定の 1 番は「作成（version 1）を履歴に入れるか」。しかしインタフェースの `action` の値の並びに `"create"` があった。
   - この 1 つの選択の上に、10 本のシナリオで約 20 件の照合が乗っていた。作成を履歴に入れなければ、それらは一斉に落ちていた。
3. **シナリオの許容が、残りの幅を吸収した。** 状態コードを幅で書かせる指示（2 周目からの工場の指示）が、戻しの成功（200 / 201）や入力の誤り（400 / 422）の違いを吸収した。

### 別の妥当な選択なら落ちていた所

作る役が別の妥当な選択をしていれば落ちていた所は、7 つある。

- 作成を履歴に入れない（約 20 件）
- 新しい順に並べる（4 件）
- 戻しで version を上げない（数件）
- `toVersion` に文字列や小数を受け付ける（3 件）
- 戻しで version を必須にしない（1 件）
- limit や cursor の誤りを丸める・無視する（約 7 件）
- 削除したメモの履歴を残して 200 を返す（1 件）

ただし、どれも既存コードやインタフェースが反対側を指していた。本当に表と裏が五分だったのは、並び順だけである。それも、両者が既存の `GET /memos` にそろえたことで当たった。

### 前提 2 についての含意

- 前提 2 を試すには、「仕様に書いていない」だけでは足りない。作る役が既存コード・インタフェース・慣習から推せない答えを、シナリオが求める必要がある。例は次のとおり。
  - 新しい順に並べる
  - 削除したメモの履歴を残す
  - `toVersion` が現在の版と同じなら 409 を返す
  - 履歴の件数に上限を設ける
- インタフェースに列挙値（`"create"` など）を書かせると、未定の項目の答えが漏れる。次の周で手を入れるなら、インタフェースの線を「名前と形」から「名前だけ」に寄せるか、列挙値を除く。どちらにするかはオーナー判断。

## 既知の限界

- **分類は 1 回だけの標本。** シナリオごとに予測を 1 回しか取っていない（2 周目からのオーナー判断）。
- **計測 (2) の決め手の付け方は、分析エージェントの判断である。**
  - A と D の境は、見る人によって動く。検証役も、10 件のうち 2 件を A から D に、1 件を D から C に付け替えた。
  - 「E が 0 件」は、作る役のコードと既存コードの対応が引用で示せた、という意味にとどまる。作る役が実際にそれを見て決めたかどうかは、記録から分からない。
- **隔離の確認で、2 つ目のモデルが使われていた。**
  - 隔離の確認の記録（`isolation-probe.json`）では、使われたモデルが `claude-opus-5-5,claude-opus-4-8` と 2 つ並んでいた。
  - 役ごとの指定は効いている。隔離の確認は、役 `builder` としてモデルを呼ぶ（`src/cli.ts`）。アダプタは役 `builder` に `--model claude-opus-5-5` を渡す（`src/adapter.ts` の `MODEL_BY_ROLE`）。
  - 2 つ目は、CLI が返すモデル別使用量（`modelUsage`）のキーに入っていた。工場が指定していないので、CLI の内部の呼び出しである（隔離の確認は、シェルのコマンドを 6 つ実行させる）。どの処理の呼び出しで、費用のうちいくらだったかは、記録から分からない。工場はモデル名だけを残し、モデル別の費用と用途を残していないためである。
  - run の作る役・判定役には、2 つ目のモデルは出ていない。`total_cost_usd` は、モデル別使用量を合算した値として計上している。
- **入口の要約の中の、未定の見出しの揺れ。** 仕様の下書き役は、見出しを `## Undecided` と正確に書いた。見出しが揺れると検査で落ち、1 回の書き直しに入る。わざと厳しくしてある。この周の仕様は、正しい見出しで入っていた。
- **シナリオの 1 行要約の中身。** 要約には、期待する選択を言葉で表したものがあった（「古い順」「2 件・2 件・1 件のページ」「作成時刻は変わらない」）。具体的な値・パス・状態コードを入れない検査には通っている。やり直しが起きていれば、収束の主な経路はここだったはずである。この周は 1 回目で合格したので、効き方は観測していない。
- **1 つの step で同じ値を 2 つの名前に取り出すと、2 つの等しさが失われる**（分類器の P3。直していない）。`unstated` が多めに出る方向にだけ効く。この周には当たらない（名前の重複 0 件）。
- **1・2 周目から引き継いでいる限界。**
  - lap 台帳には、ロックが無い。
  - 合成トラフィックは、メモ API の形に固定している。
  - アプリが 127.0.0.1 以外で待ち受けていないかは、起動時にだけ確かめる。
  - 作る役は認証トークンを読める。
