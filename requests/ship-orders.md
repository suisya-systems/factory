# Request: orders shipped through a carrier service, with retries and cancellation

An HTTP API for a shop that ships its orders through an outside carrier. Every request and response body is JSON. Ids are strings the server assigns. Dates are `YYYY-MM-DD` strings; a date that is not a real calendar date is 400.

- **The external service.** The carrier is at the base URL in `process.env.SERVICE_URL` and has two endpoints:
  - `POST /shipments` with the JSON body `{"reference": orderId, "items": [{"sku", "qty"}, ...], "address": {"name", "postalCode", "line1"}}` and an `Idempotency-Key` header. It answers 201 with `{"id": string, "trackingNumber": string}` when it accepts the shipment, 400 to 499 when it rejects it, and 500 to 599 when it fails.
  - `DELETE /shipments/{shipmentId}` (no body) answers 204 when the shipment is cancelled, 409 when the parcel was already picked up, and 500 to 599 when it fails.
  Any answer not listed above (for example a 200, or a 201 without `id` or `trackingNumber`), or no answer, is handled like a 5xx.
- **The shop's date.** The server keeps a date, `today`, starting at `2026-11-02`. `GET /clock` returns 200 with `{"today"}`. `POST /clock` with `{"today": date}` moves it forward (an earlier date is 409; the same date changes nothing and `retried` is empty). When it moves to a later date, the app first makes the retries (below), then answers 200 with `{"today", "retried": [orderId, ...]}`, the orders for which it sent `POST /shipments` during this move, in the order sent.
- `POST /products` with `{"sku": string, "stock": integer}` adds a product (sku 1 to 40 characters and unique, 409 if taken; stock 0 to 10,000). 201 with `{"sku", "stock", "reserved": 0, "available"}`, where `available` is `stock - reserved`. `POST /products/{sku}/restock` with `{"qty"}` (1 to 10,000) adds to `stock`; 200 with the product. `GET /products/{sku}` returns 200 with the product.
- `POST /orders` with `{"items": [{"sku", "qty"}, ...], "address": {"name", "postalCode", "line1"}}` creates an order: 1 to 10 items with distinct skus of existing products (an unknown sku is 404), qty 1 to 100, address strings 1 to 100 characters. Nothing is reserved or sent. 201 with the order `{"id", "status": "new", "items", "address", "confirmations": 0, "attempts": 0, "shipmentId": null, "trackingNumber": null, "holdReason": null}`.
- **Confirming.** `POST /orders/{id}/confirm` is allowed when the order is `new` or `on_hold` (409 otherwise). It adds 1 to `confirmations`, sets `attempts` to 0 and makes an attempt. 200 with the order after the attempt, whatever the carrier answered.
- **An attempt.** If any item's `qty` is more than its product's `available`, the order goes `on_hold` with `holdReason` `"stock"`, and nothing is sent. Otherwise `attempts` grows by 1 and the app sends `POST /shipments` with `reference` the order's id, the order's items in their order, its address, and the header `Idempotency-Key: {orderId}-{confirmations}`. Every attempt of one confirmation therefore sends the same key, and confirming again after a hold sends a new one. Then:
  - on 201 the order is `booked`, with `shipmentId` (the answer's `id`) and `trackingNumber`; only now is each item's `qty` added to its product's `reserved`;
  - on 400 to 499 it goes `on_hold` with `holdReason` `"carrier"`;
  - otherwise it is `retrying`, or `failed` when `attempts` has reached 3. A failed order is final.
  `holdReason` is null in every status but `on_hold`.
- **Retries.** When the clock moves to a later date, every `retrying` order makes one attempt, in the order the orders were created. A retry checks stock first like any attempt, so it may put the order on hold without sending anything, and stock reserved by an earlier retry in the same move counts.
- **Cancelling.** `POST /orders/{id}/cancel`: an order that is `new`, `on_hold` or `retrying` becomes `cancelled` at once and nothing is sent (a retrying order is not retried again). For a `booked` order the app sends `DELETE /shipments/{shipmentId}`: on 204 the order is `cancelled` and its quantities leave `reserved`; on 409 the cancel is refused with 409 and the order stays `booked`; on anything else it is refused with 503 and the order stays `booked`. Any other status is 409 and nothing is sent. 200 with the order.
- `POST /orders/{id}/handover` records that the carrier collected a `booked` order: it becomes `shipped`, and its quantities leave both `stock` and `reserved`. 409 for any other status. Nothing is sent.
- `GET /orders/{id}` returns 200 with the order. `GET /orders?status=...` returns 200 with the orders in creation order, only those with that status when given (one of `new`, `on_hold`, `retrying`, `booked`, `failed`, `cancelled`, `shipped`; another value is 400).
- Errors: a body that is not valid JSON, a missing or wrong-typed field, or a value outside the rules above is 400; an unknown order or product is 404; the conflicts named above are 409. A refused request changes nothing. Every error body is `{"error": string}`.
- Data is kept in memory; it does not have to survive a restart.
