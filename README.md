# factory
L5 software factory prototype (spec + hidden scenarios -> build -> judge -> ship)

Design: `design/grand-design.md` in the suisya-systems/factory-notes repository. The records of each run (lap 1 to 6: the runbook written before the run, the report, and for laps 5 and 6 the pre-registration, check scripts and reference apps) are in `laps/` in the same repository.

One command per lap: `npm run factory -- lap <definition.json>` runs a lap's whole procedure from a definition file the creator writes (examples: [examples/lap-6.json](examples/lap-6.json), lap 6 as a definition, and [examples/lap-7.json](examples/lap-7.json), the definition lap 7 ran with, its tools under `docs/lap-7/` kept in factory-notes `laps/lap-7/`; the scripts and pre-registration it names under `docs/lap-6/` are kept with the lap 6 records in factory-notes `laps/lap-6/`; to rerun it, put them back under `docs/lap-6/`, since the scripts import `../../src`). It stops only at a human gate (exit 3) with one line naming the summary to read and the resume command; the owner approves with `lap <definition> --approve <gate> --by <name> --version <hash>`, and the same `lap <definition>` resumes, skipping finished steps. A failed or interrupted step (error, cost cap, emergency stop) fails the lap (exit 1) and is never re-run.

Emergency stop: `npm run factory -- stop` creates `.factory/STOP` (or SIGTERM the factory). While that file exists every command refuses to start; delete it by hand to resume.
Cost caps: per change (`--max-cost`, default $10, drafter spend included) and per lap ($30, `.factory/lap-ledger.jsonl`, all commands). Before each model call the lap cap is checked against the summed ledger minus the budgets of the calls still in flight, so runs in parallel cannot take it past the cap (only a call that spends more than its own budget can).

## Terms

- **change**: one request taken through the loop (draft, approve, build, judge, ship, observe), identified by a change id such as `memo-api-1`.
- **spec drafter / scenario drafter**: since lap 2, two separate model sessions draft one change. The spec drafter writes the spec, the assumptions and the **interface** (endpoint, parameter and field names and response shapes only, no rules). The scenario drafter writes the hidden scenarios from the request, the existing app and the interface only. It never sees the spec or the spec drafter's other assumptions: in lap 2 those assumptions carried nearly every rule of the spec, so the owner decided on 2026-10-17 to pass the interface only. Since lap 4 the interface holds names, never the values a field or parameter may take: in lap 3 an enumerated value decided an Undecided point. The factory rejects an interface entry that is not a bare name (so `action: create|update` cannot pass); a value spelled as a name can, so the approver checks the interface. Since lap 3 the spec is deliberately coarse (owner decision 2026-10-17): it states only what the request says plus the interface, and lists every behaviour the request leaves open (defaults, status codes, boundaries, combinations) under a final `## Undecided` section without deciding it. The builder decides those points.
- **base**: for a change that extends an app, the commit of the ship target the drafters read (`draft --base`). It is part of the approved version, and `run` fails if the ship target has moved.
- **lap**: one owner-budgeted run of the factory; its ledger (`.factory/lap-ledger.jsonl`) sums the cost of every model call of every change and command. Since #13 it is append-only: before a call a `hold` line reserves the call's whole budget, after it a charge line (`usd`, `byModel`) settles it; totals are sums. A hold never settled (the process died mid-call) counts in full. A state dir from before #13 has `lap-ledger.json` (the totals); it is still counted, never written. Since lap 4 every ledger (lap, `draft-cost.json`, `run.json`) also splits the cost per role and model (`byRoleModel`, from the CLI's per-model usage); cost no model was reported for is under `(unattributed)`.
- **vault**: `.factory/vault/`, where the hidden scenarios and the approved set live. No sandboxed process (builder, judge model session, app code) can see it.
- **inSpec (self-report)**: per scenario, the drafter's own claim. In lap 1 it meant "the spec states this behaviour". Since lap 2 the scenario drafter cannot see the spec, so it means "the request states this behaviour". The two laps' self-reports answer different questions. It is not verified.
- **classification (independent label)**: per scenario, decided by a procedure instead of the drafter. A separate session sees only the spec, the existing app code and the scenario's requests (no expectations, ids, titles or summaries), and predicts each response. The scenario's checks are compared with the prediction mechanically. Labels:
  - `readable`: every check is satisfied. The basis is `spec`, `code` or `convention` (general HTTP habit). A claimed spec/code basis counts only if its quote is really in the spec/code.
  - `contradicts`: the spec or code says something else.
  - `unstated`: the spec leaves something the scenario checks open.
  - `unknown`: the classifier failed.

  It is fixed at approval (`classification.json` in the vault), and pass rates are split on it.
- **discrepancy list**: the part of the approval summary that lists `contradicts` scenarios, under (a), and `unstated` ones with the open checks, under (b). The factory never fixes them. The owner approves the set as it is, or drafts a new change.
- **canary**: a random string that `probe-isolation` plants in the vault. If it appears in the builder's reply or files, the vault leaked.
- **model per role**: `MODEL_BY_ROLE` in `src/adapter.ts` pins the model of each role (`spec-drafter`, `scenario-drafter`, `classifier`, `builder`, `judge`); a role missing from it is an error. Since lap 5, `--model <role>=<model>` (draft, replicate, probe-isolation) overrides it for one command and is recorded as `requestedModels`.
- **replicate**: since lap 5, K independent single builds of one approved spec, each in an empty repository, scored by the hidden scenarios of that change and of `--score` changes with the same spec (`draft --spec-from`), and by probes. No LLM judge, no retry, nothing ships. `run` and `replicate` are not mixed on one change.
- **probe / decision**: a decision is a point the spec leaves open with a few pre-registered answers; its probe is a request sequence written by the experimenter that tells the answers apart from the responses (`other` = none matched, `blocked` = it could not run). Probes live in the vault, never with a builder.
- **control spec**: `draft --spec-from <id> --spec <file>`: the approved spec of `<id>` with its body replaced by hand (lap 5: the sentences that came from one request sentence removed), the interface kept byte for byte.
- **minority choice**: since lap 6, `draft --minority` asks the scenario writer to pick, on purpose, reasonable answers most builders would not, and to mark each in its assumptions as `[minority] <point>: <answer> (most would: <usual answer>); scenarios: <ids>`. The approval summary lists them; the builder never sees them. Since lap 7, `--minority-brief <text>` adds the experimenter's constraints on those points (how many, which kind) to the scenario writer's prompt; the text is kept in the assumptions as `(experimenter) minority brief: <text>`, so it is part of the approved version.
- **feedback mode**: since lap 7, `run --feedback bare` is a control: a rejected builder gets one `- failed: a hidden scenario` line per failed scenario (and the LLM judge line), never the summaries. The default `summaries` is the normal loop. The mode is recorded as `feedback` in `run.json`.
- **external service (fake)**: since #17, `draft --service` declares that the app calls an external service the request describes. The factory appends a fixed `## External service (factory)` section to the spec (the builder learns only that the service is at `process.env.SERVICE_URL`; its contract lifts "no network" for that address), and the scenario writer may add steps with `"service": true`, which go to the fake's control endpoint instead of the app: `POST /responses` `{method, path, status, json?, headers?}` sets what the fake answers (path without query, the last one wins, anything unset gets 404), and `GET /requests` returns the requests the app sent, in order (`method`, `path` with query, lower-case `headers`, `body`). While judging (run, replicate) each scenario gets a fresh fake; service steps before the first app step run before the app starts. The fake has no listener of its own (builder sessions share the host network): it lives in the factory process, the app reaches it only through its own bridge (its loopback `SERVICE_URL`), and scenario steps call it directly. Past 100 requests, 64 KB per body or 512 KB in all, the scenario fails. A set-the-answer step never counts for the classification. Limits: production has no fake (`SERVICE_URL` is unset there), probes cannot use it, one HTTP service per app.
- **lap definition**: JSON with `name`, optional `home` (the FACTORY_HOME of the lap) and `steps`. Each step is one of:
  - `factory`: argv of a factory command (draft, run, replicate, tally, probe-isolation, observe), never a shell string, so no word splitting. `{state}` in an arg is the state dir. A `run` that used up its attempts counts as finished (a result); any other failed run fails the lap. `newShipTarget` (run only) creates a fresh ship target `$STATE/ship/<id>` with that README.
  - `exec`: argv of any other program (tests, the lap's own tools).
  - `copy`: an approved vault set copied `from` another state dir or `to` other change ids, checked file by file and against its approval.
  - `gate`: a human stop. `approve` lists drafts for entrance approval, `fix` maps a path in the state dir to a file it is fixed from (the pre-registration, probes; read-only afterwards, never changed), `read` lists more files the approver reads. A file not written yet keeps the lap waiting there. The gate's version covers the whole definition and those files: any change after approval stops the lap at the gate again.
  - `always: true` (exec, tally, observe): runs even after a failed step, for the lap's report (while the STOP file exists, only `exec` ones run).
  - `parallel` (since #13): a list of independent `factory run` steps (or of `factory replicate` steps, not both) with `max`, how many run at once: `{ "parallel": [{ "factory": ["run", "a", "--port", "8797"], "newShipTarget": "# app\n" }, { "factory": ["run", "b", "--port", "8798"], "newShipTarget": "# app\n" }], "max": 4 }`. The steps of a group need distinct change ids, and runs distinct `--port`s (default 8787) and ship targets, so changes to one app stay sequential steps. Each step keeps its own progress as above. After the first failure in the group (or a STOP) no further step of it starts; the running ones finish.

  Production is per port: `$STATE/prod/<port>/` holds the live release link `current` (to `releases/<sha>` there), the server pid, the access and error logs, the app data and `signals.json`; `observe --port N` reads that port's logs. Runs in one group never touch each other's prod. `run` refuses to ship into a state dir with the prod layout from before #13 (`prod/server.pid`, `prod/data`, `releases/current`); it is not migrated.

  Progress is kept in `$STATE/laps/<name>/` per step content: editing a step makes it a new step. The definition is trusted like code (an `exec` step can run anything); the owner approves it at every gate. A step finished just before the process was killed is reported as interrupted, not re-run.
- **`ponytail:` comments**: mark a deliberate simplification with a known limit and the upgrade path.
