# factory
L5 software factory prototype (spec + hidden scenarios -> build -> judge -> ship)

Design: `design/grand-design.md` in the suisya-systems/factory-notes repository. The records of each run (lap 1 to 6: the runbook written before the run, the report, and for laps 5 and 6 the pre-registration, check scripts and reference apps) are in `laps/` in the same repository.

One command per lap: `npm run factory -- lap <definition.json>` runs a lap's whole procedure from a definition file the creator writes (examples: [examples/lap-6.json](examples/lap-6.json), lap 6 as a definition, and [examples/lap-7.json](examples/lap-7.json), the definition lap 7 ran with, its tools under `docs/lap-7/` kept in factory-notes `laps/lap-7/`; the scripts and pre-registration it names under `docs/lap-6/` are kept with the lap 6 records in factory-notes `laps/lap-6/`; to rerun it, put them back under `docs/lap-6/`, since the scripts import `../../src`). It stops only at a human gate (exit 3) with one line naming the summary to read and the resume command; the owner approves with `lap <definition> --approve <gate> --by <name> --version <hash>`, and the same `lap <definition>` resumes, skipping finished steps. A failed or interrupted step (error, cost cap, emergency stop) fails the lap (exit 1) and is never re-run.

Emergency stop: `npm run factory -- stop` creates `.factory/STOP` (or SIGTERM the factory). While that file exists every command refuses to start; delete it by hand to resume.
Cost caps: per change (`--max-cost`, default $10, drafter spend included) and per lap ($260 since lap 9, $150 in lap 8, $30 before; `.factory/lap-ledger.jsonl`, all commands). Calls of a model whose spend is not reported in USD (the second family below) are $0 in USD and capped by count per lap (199). Before each model call the lap cap is checked against the summed ledger minus the budgets of the calls still in flight, so runs in parallel cannot take it past the cap (only a call that spends more than its own budget can).

Setup: Node.js 22, bubblewrap, then `npm ci` and, for apps with browser pages (`draft --ui`), the pinned headless browser: `npx playwright-core install --with-deps --only-shell chromium` (the system libraries need root; without `--with-deps` on Ubuntu 24.04: `libnspr4 libnss3 libasound2t64`). Playwright puts it in `~/.cache/ms-playwright`; set `PLAYWRIGHT_BROWSERS_PATH` to put it elsewhere, and keep it set for every factory command (the factory mounts that directory read-only into the browser's sandbox). It must not be inside the state dir.

## Terms

- **change**: one request taken through the loop (draft, approve, build, judge, ship, observe), identified by a change id such as `memo-api-1`.
- **spec drafter / scenario drafter**: since lap 2, two separate model sessions draft one change. The spec drafter writes the spec, the assumptions and the **interface** (endpoint, parameter and field names and response shapes only, no rules). The scenario drafter writes the hidden scenarios from the request, the existing app and the interface only. It never sees the spec or the spec drafter's other assumptions: in lap 2 those assumptions carried nearly every rule of the spec, so the owner decided on 2026-10-17 to pass the interface only. Since lap 4 the interface holds names, never the values a field or parameter may take: in lap 3 an enumerated value decided an Undecided point. The factory rejects an interface entry that is not a bare name (so `action: create|update` cannot pass); a value spelled as a name can, so the approver checks the interface. Since lap 3 the spec is deliberately coarse (owner decision 2026-10-17): it states only what the request says plus the interface, and lists every behaviour the request leaves open (defaults, status codes, boundaries, combinations) under a final `## Undecided` section without deciding it. The builder decides those points.
- **plan / part / whole** (since #18): a request too big for one change. `split <plan> --request <file>` has a splitter model propose 2 to 6 ordered parts (each a self-contained request, part 1 a new app, later parts extending it) and drafts the whole request as an ordinary change `<plan>-whole`; `approve <plan>` approves the parts and that whole draft in one act, bound to one version. `plan <plan> --ship-target <repo>` then builds the parts in order and stops (exit 3) at each part's own entrance approval, because a part is drafted (`--base` = the ship target) only after the one before it shipped; the plan's interface (from `<plan>-whole`) binds every part's interface (`draft --iface-from`: its names must be within it). A plan can extend an app that already exists: `split <plan> --request <file> --base <repo> [--base-path <path>] [--contract <file>]` drafts `<plan>-whole` against that repo, and the plan then drafts every part, part 1 too, against the ship target with the same paths and contract (the ship target must be at the commit the whole was drafted against); the splitter is shown the existing app. A part rejected after its attempts (a real verdict, not a failed call) is retried as a new change `<id>-r2`.. (`--retries`, default 1, at most 3) with the same approved set; if it still fails, or fails any other way (cost cap, STOP, error), the plan stops and later parts are not started. A run left `running` is never rebuilt. The ship target must be at the previous part's shipped commit before each draft and run. After the last part the scenarios of `<plan>-whole` run (no model) on the final commit: all pass = done (exit 0), else the plan fails and nothing is patched. `--max-cost` is per run, as for `run`; a retry's cap does not count the drafter's spend (the lap cap still binds). Files: `runs/<plan>.plan/` (`plan.json`, `chain.json`, `result.json`, `whole.json`).
- **base**: for a change that extends an app, the commit of the ship target the drafters read (`draft --base`). It is part of the approved version, and `run` fails if the ship target has moved. `--base-path <path>` (repeatable) shows the drafters (and the classifier) only the tracked text files at or under those repo-relative paths, because the whole app is pasted into their prompts and may not pass 200,000 characters (the error names the largest directories); `<file>:START-END` (1-based, inclusive; repeatable, overlapping ranges are joined, an end past the file is clamped) pastes only those lines of one file, for a file that alone is too big: the lines outside are given to nobody but the builder (so a hint outside the range can be missed by the drafters and the classifier). The other files are listed by name in a first `=== NOT SHOWN` line, and the builder, which works in a clone of the whole repository, sees them all. The paths are part of the approved version (`paths` in `base.json`; absent when the whole app was shown, so older approvals keep their version).
- **lap**: one owner-budgeted run of the factory; its ledger (`.factory/lap-ledger.jsonl`) sums the cost of every model call of every change and command. Since #13 it is append-only: before a call a `hold` line reserves the call's whole budget, after it a charge line (`usd`, `byModel`) settles it; totals are sums. A hold never settled (the process died mid-call) counts in full. An `event` line (since #32: a redraft, with its reason) moves no money. A state dir from before #13 has `lap-ledger.json` (the totals); it is still counted, never written. Since lap 4 every ledger (lap, `draft-cost.json`, `run.json`) also splits the cost per role and model (`byRoleModel`, from the CLI's per-model usage); cost no model was reported for is under `(unattributed)`.
- **vault**: `.factory/vault/`, where the hidden scenarios and the approved set live. No sandboxed process (builder, judge model session, app code) can see it.
- **inSpec (self-report)**: per scenario, the drafter's own claim. In lap 1 it meant "the spec states this behaviour". Since lap 2 the scenario drafter cannot see the spec, so it means "the request states this behaviour". The two laps' self-reports answer different questions. It is not verified.
- **classification (independent label)**: per scenario, decided by a procedure instead of the drafter. A separate session sees only the spec, the existing app code and the scenario's requests (no expectations, ids, titles or summaries), and predicts each response. The scenario's checks are compared with the prediction mechanically. Labels:
  - `readable`: every check is satisfied. The basis is `spec`, `code` or `convention` (general HTTP habit). A claimed spec/code basis counts only if its quote is really in the spec/code.
  - `contradicts`: the spec or code says something else.
  - `unstated`: the spec leaves something the scenario checks open.
  - `unknown`: the classifier failed.

  It is fixed at approval (`classification.json` in the vault), and pass rates are split on it.
- **discrepancy list**: the part of the approval summary that lists `contradicts` scenarios, under (a), and `unstated` ones with the open checks, under (b). The factory never fixes them. The owner approves the set as it is, or drafts a new change.
- **Undecided the request may decide**: since #52, the top of the approval summary lists Undecided items that ask whether body fields must be present, when the request's line for that endpoint already writes those fields into the body (`"f"` required, `"f"?` optional), with that line and the request's missing-field rule. In lap 11 the spec moved "PUT /users/{id} takes `{"mode", "muted"}`" to Undecided, every builder accepted a partial body, and every build failed the scenario that followed the request. The check calls no model and only shows; the owner decides, and drafts a new change if the request decides the point.
- **canary**: a random string that `probe-isolation` plants in the vault. If it appears in the builder's reply or files, the vault leaked. Since lap 8 the probe also fails if a second-family login secret appears there (only true / false is recorded).
- **model per role**: `MODEL_BY_ROLE` in `src/adapter.ts` pins the model of each role (`spec-drafter`, `scenario-drafter`, `classifier`, `builder`, `judge`); a role missing from it is an error. Since lap 5, `--model <role>=<model>` (draft, replicate, probe-isolation) overrides it for one command and is recorded as `requestedModels`. Since lap 8 the drafters (`spec-drafter`, `scenario-drafter`) may also use a second model family, `gpt-6-astra` through the Codex CLI (found on PATH; its ChatGPT login is mounted into that drafter's sandbox only, never a builder's). Every call is listed in the draft's `draft-cost.json` (`calls`: role, requested model, reported model), with `specFrom` for a reused spec.
- **replicate**: since lap 5, K independent single builds of one approved spec, each in an empty repository (for a change drafted with `--base`, `replicate --base <repo>` starts each build as a clone of that repo, whose HEAD must be the approved base), scored by the hidden scenarios of that change and of `--score` changes with the same spec (`draft --spec-from`), and by probes. No LLM judge, no retry, nothing ships. `run` and `replicate` are not mixed on one change.
- **probe / decision**: a decision is a point the spec leaves open with a few pre-registered answers; its probe is a request sequence written by the experimenter that tells the answers apart from the responses (`other` = none matched, `blocked` = it could not run). Probes live in the vault, never with a builder.
- **control spec**: `draft --spec-from <id> --spec <file>`: the approved spec of `<id>` with its body replaced by hand (lap 5: the sentences that came from one request sentence removed), the interface kept byte for byte.
- **minority choice**: since lap 6, `draft --minority` asks the scenario writer to pick, on purpose, reasonable answers most builders would not, and to mark each in its assumptions as `[minority] <point>: <answer> (most would: <usual answer>); scenarios: <ids>`. The approval summary lists them; the builder never sees them. Since lap 7, `--minority-brief <text>` adds the experimenter's constraints on those points (how many, which kind) to the scenario writer's prompt; the text is kept in the assumptions as `(experimenter) minority brief: <text>`, so it is part of the approved version.
- **feedback mode**: since lap 7, `run --feedback bare` is a control: a rejected builder gets one `- failed: a hidden scenario` line per failed scenario (and the LLM judge line), never the summaries. The default `summaries` is the normal loop. The mode is recorded as `feedback` in `run.json`.
- **external service (fake)**: since #17, `draft --service` declares that the app calls an external service the request describes. The factory appends a fixed `## External service (factory)` section to the spec (the builder learns only that the service is at `process.env.SERVICE_URL`; its contract lifts "no network" for that address), and the scenario writer may add steps with `"service": true`, which go to the fake's control endpoint instead of the app: `POST /responses` `{method, path, status, json?, headers?}` sets what the fake answers (path without query, the last one wins, anything unset gets 404), and `GET /requests` returns the requests the app sent, in order (`method`, `path` with query, lower-case `headers`, `body`). While judging (run, replicate) each scenario gets a fresh fake; service steps before the first app step run before the app starts. The fake has no listener of its own (builder sessions share the host network): it lives in the factory process, the app reaches it only through its own bridge (its loopback `SERVICE_URL`), and scenario steps call it directly. Past 100 requests, 20 open connections, 64 KB per body or 512 KB in all (counted as they arrive, unfinished requests included), the fake cuts the connection and the scenario fails. A set-the-answer step never counts for the classification. Limits: production has no fake (`SERVICE_URL` is unset there), probes cannot use it, one HTTP service per app.
- **signal watch** (since #19): `watch --ship-target <repo> (--once | --interval SEC) [--port N]` polls `$STATE/prod/<port>/signals.json` (refreshed from the logs with `observe` first) for every port, or port N. A sign of failure (`errors5xx` or `stderrErrors` above 0; 4xx and latency do not count) that was not seen before becomes an ordinary `draft` named `sig-<port>-<hash>` (`--base` = the ship target) and stops for approval; `watch` never approves, runs or ships. A sign is fingerprinted by its normalised sample (no time, digits as `#`, no query, no counts), kept in `$STATE/signal-seen.json`, so the same failure is drafted once; the fingerprint is recorded only after the draft succeeded. At most 3 signal drafts may wait for approval at a time. The loop ends at the STOP file or at the first failed draft. Limits: `observe` keeps the last 5 samples, so a failure that leaves that window and returns is drafted once more; abandoned drafts count as waiting (there is no reject command).
- **browser UI**: since #4, `draft --ui` declares that the app has pages a user works in a browser. The factory appends a fixed `## Browser UI (factory)` section to the spec (the app serves its pages itself; the elements named under the interface key `testIds`, bare names, carry `data-testid`), and the scenario writer may add steps with `"ui"`: `{"ui": "goto", "path"}`, `{"ui": "fill", "target", "text"}`, `{"ui": "click", "target"}`, where a target is `<testId>` (the only visible one) or `<testId>.<n>` (the n-th visible, 0-based). After a ui step its optional `expect` / `capture` read the page as JSON, `{"<testId>": [visible text of each visible element with that id, in page order]}` (an input gives its value; `status` is the page's for goto only), retried for up to 5 s, so the usual checks apply (`"length": {"memoItem": 0}` = none visible). While judging (run, replicate, the whole check of a plan) each scenario with ui steps gets a fresh headless Chromium (Playwright, `playwright-core` pinned) in its own sandbox: loopback only, `$HOME` and `/tmp` hidden, its own pid namespace (the app cannot see it), none of the factory's environment. Playwright drives it over a pipe (no debugging port); a relay inside its sandbox carries the browser's connections to the app's port, the only address it can reach. The page is read in an isolated world, so page JS cannot bend what the judge reads, and expected values never enter the browser. Every browser operation is bounded (10 s) and stops with the emergency stop. Limits: a page showing more than 500 elements with a test id or 64,000 characters of their text fails the step; no keyboard, hover, select, file or multi-tab actions; probes stay HTTP only; linux x64 only.
- **command-line program (run step)**: `draft --contract <file>` declares that the app is a command-line program, not an HTTP server (it does not go with `--service` or `--ui`). The contract file is JSON, `{"command": ["python3", "-m", "pkg.cli"], "pythonPath": ["src"], "deps": "<sha256 of a lock file>"}`: the argv the factory runs (`{app}` in a word = the exported repository), the repository directories put on `PYTHONPATH`, and optionally a dependency set. The factory appends a fixed `## Command-line program (factory)` section with the contract to the spec (so the approved version covers it; the builder's run contract then names the command and no server), the interface may name `commands`, `flags` (per command) and `files` besides `fields`, and the scenario writer's steps are all `run` steps: `{"run": [args after the command], "stdin", "files": {path: string or JSON}, "read": [paths], "env": {NAME: value}, "expect", "capture"}`. Each scenario gets one empty working directory that its steps share (`files` are written there before the run, the program's current directory); the program runs in its own sandbox as a ui step's browser does (loopback-only namespace, `$HOME` and `/tmp` hidden, the repository read-only, 20 s, 200,000 characters of output). Its response is checked by the usual checks: `status` is the exit code and the body is `{"stdout": <parsed as JSON when it is JSON, else the text>, "stderr": <text>, "files": {<path>: <parsed JSON or text>}}` with the files named in `read` (a file not written is absent; the dot paths of `length`, `jsonHas` and `capture` reach a file `out/plan.json` as `files.out/plan.json`). The summary rule covers the arguments that are not sub-command words or flags, the file paths and contents, stdin and env values. A program is shipped by the fast-forward of the ship target alone: no smoke start, no `serve`, no synthetic traffic, no `observe` (`signals` is null). Limits: `user-judge` and `probe`s do not take a program (HTTP and pages only), the classifier predicts standard output best when it is JSON, a scenario cannot mix run steps with HTTP, service or ui steps.
- **dependency set**: a Python dependency set is a virtualenv made by the operator, outside `$HOME` and outside `/tmp`, `/mnt`, `/run` and `/var/tmp` (the sandboxes hide those), from hash-pinned wheels only, no index and no network: `FACTORY_DEPS=/opt/factory-deps npm run factory -- deps build --lock requirements.lock --wheelhouse wheels/` (the lock is pip's `--require-hashes` form, e.g. from `uv pip compile --generate-hashes`, the wheelhouse from `pip download --require-hashes -d wheels -r requirements.lock`; `python3 -m venv` needs the `python3-venv` package). The set lives in `$FACTORY_DEPS/<sha256 of the lock file>/` (default `/opt/factory-deps`) and a contract names it by that hash (`"deps"`), so the set is part of the approved spec and a change of the dependencies is a new draft; plan parts must carry the same contract. A run puts its `venv/bin` first on `PATH`; the sandboxes mount `/` read-only, so the builder sees the same set (the builder's contract text names the packages and the set's python). The set is not re-hashed when judging: whoever can write the root can change it, so keep it root-owned. The builder's model session is not cut off from the network (as before): that the builder installs nothing is still the run contract's instruction only.
- **user-agent judging (separate arm)**: since #30, `user-judge <id> --request <file> [--sessions 0-5] [--max-cost N]` has a user agent (role `user-agent`, no tools) use each build `run` or `replicate` recorded for `<id>` and say whether it does the job the request describes: `{"satisfied", "reason", "problems"}`. It decides nothing: it runs after them, reads their records and writes only `runs/<id>/user/` (one record per build, user-agent model and session) and `compare.md`, which sets each session's verdict beside the verdict that counted (a run attempt's pass; for a replicate build, all of this change's scenarios). It sees the request (its sha256 must be the one the change was drafted from), the interface and what its own actions got back, never the scenarios, assumptions, classification, spec body, code or the current judge's results. Each session is one app kept running (with its fake and browser, as for a scenario); the agent writes up to 8 actions per turn as JSON (HTTP, service and ui steps without checks), the factory sends them and shows the status, headers and body (or the page), cut to 1,500 characters; at most 6 turns. A session is claimed (its record created) before any spend and never run again; an interrupted one shows as such. Caps: $0.5 per call (`CAPS.userCallUsd`), `--max-cost` (default $10) over every `user-judge` of the change, apart from its draft and build spend; the lap cap binds. Since #50, session k of a build leans on one focus (main, input, state, failure, cycling; in the record and its name), and `--mutants <file under vault/>` adds seeded-defect builds: `[{"id", "build", "file", "find", "replace", "defect"}]`, `find` occurring exactly once in `file` of that recorded build. Each mutant is scored by the change's scenarios before any model call (so `--sessions 0` is a free check), its sessions are never told, and `compare.md` counts the sessions that said no to it (caught), per focus. The verdict stays advisory: it never counts toward pass / fail. Design and the owner decisions: factory-notes `design/user-judge.md`.
- **lap definition**: JSON with `name`, optional `home` (the FACTORY_HOME of the lap) and `steps`. Each step is one of:
  - `factory`: argv of a factory command (draft, run, replicate, tally, probe-isolation, observe, user-judge), never a shell string, so no word splitting. `{state}` in an arg is the state dir. A `run` that used up its attempts counts as finished (a result); any other failed run fails the lap. `newShipTarget` (run only) creates a fresh ship target `$STATE/ship/<id>` with that README. `redraft: N` (draft only, 1 to 3; since #32): a draft that fails (an error or a rejected reply, not a cost cap or a STOP) is drafted again as `<id>-r2`, `<id>-r3`.., at most N times, without changing the definition. Every later step still names it `<id>`: in a step's args (a whole arg, or a piece of a path, a comma list or `--opt=`), a gate's `approve` and a `copy`, `<id>` stands for the name it was drafted as. The failed draft's spend stays in the lap ledger (the lap cap counts it); each redraft and its reason is an `event` line there and a section of the next gate's summary. A gate's version binds the redrafts before it, so a redraft after an approved gate never asks it again. No other step may draft `<id>` or the names it may take.
  - `exec`: argv of any other program (tests, the lap's own tools).
  - `copy`: an approved vault set copied `from` another state dir or `to` other change ids, checked file by file and against its approval.
  - `gate`: a human stop. `approve` lists drafts for entrance approval, `fix` maps a path in the state dir to a file it is fixed from (the pre-registration, probes; read-only afterwards, never changed), `read` lists more files the approver reads. A file not written yet keeps the lap waiting there. The gate's version covers the whole definition and those files: any change after approval stops the lap at the gate again.
  - `always: true` (exec, tally, observe): runs even after a failed step, for the lap's report (while the STOP file exists, only `exec` ones run).
  - `parallel` (since #13): a list of independent `factory run` steps (or of `factory replicate` steps, not both) with `max`, how many run at once: `{ "parallel": [{ "factory": ["run", "a", "--port", "8797"], "newShipTarget": "# app\n" }, { "factory": ["run", "b", "--port", "8798"], "newShipTarget": "# app\n" }], "max": 4 }`. The steps of a group need distinct change ids, and runs distinct `--port`s (default 8787) and ship targets, so changes to one app stay sequential steps. Each step keeps its own progress as above. After the first failure in the group (or a STOP) no further step of it starts; the running ones finish.

  Production is per port: `$STATE/prod/<port>/` holds the live release link `current` (to `releases/<sha>` there), the server pid, the access and error logs, the app data and `signals.json`; `observe --port N` reads that port's logs. Runs in one group never touch each other's prod. `run` refuses to ship into a state dir with the prod layout from before #13 (`prod/server.pid`, `prod/data`, `releases/current`); it is not migrated.

  Progress is kept in `$STATE/laps/<name>/` per step content: editing a step makes it a new step. The definition is trusted like code (an `exec` step can run anything); the owner approves it at every gate. A step finished just before the process was killed is reported as interrupted, not re-run.
- **`ponytail:` comments**: mark a deliberate simplification with a known limit and the upgrade path.
